# Новая Архитектура Системы Сохранений 

Новая система сохранений мира была полностью переработана для обеспечения максимальной производительности, отказоустойчивости и устранения микрофризов (stuttering) во время игры. Ниже описаны ключевые компоненты и механики.

## 1. Региональный Формат (`.zld`)

Вместо сохранения каждого чанка (16×16×16) в отдельный файл, мир разбит на огромные **Регионы**.
- **Размер региона:** 16×16×16 чанков. Это означает, что один файл региона покрывает объем 256×256×256 вокселей.
- **Файловая структура:** Регионы сохраняются в папке `region/` под именами формата `r.X.Y.Z.zld` (например, `r.0.-1.0.zld`).
- **Заголовок:** Каждый файл начинается с фиксированного заголовка (48 КБ), который содержит таблицу поиска. Для каждого из 4096 возможных чанков в заголовке записаны 2 значения:
  1. `offset` (смещение байтов от начала файла)
  2. `size` (размер сжатого чанка в байтах)

Такой подход минимизирует количество файлов на жестком диске (не нагружает файловую систему ОС) и позволяет мгновенно обращаться к любому чанку внутри региона.

## 2. Аллокатор Свободного Места (FreeSpaceMap)

Поскольку размеры сжатых чанков постоянно меняются (пустой чанк занимает мало места, а сложная постройка — много), нам нужно переиспользовать освободившееся место внутри файла региона:
- При обновлении чанка старый блок данных помечается как "свободный".
- Движок использует **Free Space Map**, чтобы находить наиболее подходящие по размеру "дыры" в файле для записи новых данных.
- Если подходящей "дыры" нет, новые данные дописываются в конец файла.
- Периодически вызывается процесс `compact_and_flush`, который убирает пустоты и дефрагментирует файлы `.zld`.

## 3. Сжатие Zstandard (Zstd)

Мы отказались от устаревшего DEFLATE (`flate2`) в пользу современного **Zstandard (zstd)** с уровнем компрессии 3.
- **Скорость:** Распаковка данных происходит в 3-4 раза быстрее, что критически важно для плавного геймплея при беге.
- **Сжатие:** Алгоритм Zstd обеспечивает отличную степень сжатия сырых воксельных данных, экономя место на диске.

## 4. Грязные Флаги (Dirty Flags) и Автосохранение

Чтобы избежать потери прогресса при сбоях (краш игры, отключение света), внедрена система фонового автосохранения.
- **Флаг `is_dirty`**: У каждого чанка в памяти есть булевый флаг. Как только игрок ломает/ставит блок, или происходит обновление освещения, флаг чанка становится `true`.
- **Таймер**: Главный цикл игры (`update_timing`) проверяет таймер. Каждые 30 секунд движок сканирует мир.
- **Фоновый экспорт**: Все чанки с `is_dirty = true` клонируются и отправляются в отдельный рабочий поток (thread), где происходит их Zstd-сжатие и запись на диск. Игровой поток не блокируется ни на миллисекунду.

## 5. Атомарное сохранение Метаданных

Файлы с критической информацией о мире (`level.json`) и игроке (`player.json`) больше не перезаписываются напрямую.
- Сначала данные сохраняются во временные файлы `.tmp` (например, `level.json.tmp`).
- Затем, когда запись успешно завершена, ОС выполняет мгновенную атомарную операцию переименования `fs::rename`.
- Это полностью исключает риск коррупции JSON-файлов, если компьютер выключится ровно в момент записи.

## 6. Асинхронная Фоновая Загрузка (Streaming)

Раньше игра фризила (заикалась), когда игрок заходил в новые территории, так как генерация или чтение с диска останавливали главный поток.
- Теперь функция `ensure_terrain_around` использует `chunk_mesh_pool` (пул потоков).
- Когда требуется новый чанк, фоновый поток **сначала проверяет наличие файла региона на диске**.
- Если игрок уже был в этом месте, чанк мгновенно читается с диска (Read) и распаковывается через Zstd.
- Если файла нет — запускается процедурная генерация.
- Готовый чанк асинхронно отправляется в главный поток через каналы (`mpsc::Receiver`), обеспечивая абсолютно бесшовный и плавный игровой опыт (seamless streaming).
